# 7월 15~16일 개발 인수인계

## 시작

처음 받는 경우 저장소를 내려받고 `develop` 브랜치로 이동한다.

```bash
git clone https://github.com/aivle-b-t24/ai-s-eye.git
cd ai-s-eye
git switch develop
cp .env.example .env
```

프로젝트 루트에서 다음 명령을 실행한다.

`docker compose up --build -d`

컨테이너 상태 확인:

`docker compose ps`

정상 상태 확인:

`curl http://localhost:8000/health`

Swagger:

`http://localhost:8000/docs`

대시보드:

`http://localhost:5173`

## 로그와 재시작

API 로그:

`docker compose logs -f api`

DB 로그:

`docker compose logs -f db`

대시보드 로그:

`docker compose logs -f dashboard`

API 재시작:

`docker compose restart api`

코드 변경 후 다시 빌드:

`docker compose up --build -d api`

대시보드 패키지나 Docker 설정 변경 후 다시 빌드:

`docker compose up --build -d dashboard`

전체 종료:

`docker compose down`

## 담당별 연결 지점

### 비전

- `packages/contracts/store_state.schema.json` 형식으로 데이터를 만든다.
- `POST /internal/store-states`로 전송한다.
- API 주소는 환경변수로 받는 형태를 권장한다.

### AICC

- 매장 상태: `GET /api/stores/{store_id}/state`
- ETA: `GET /api/stores/{store_id}/eta`
- 메뉴: `GET /api/stores/{store_id}/menus`
- 정책: `GET /api/stores/{store_id}/policies`

### 프론트엔드

- 개발 서버 기본 Origin인 `http://localhost:5173`은 허용돼 있다.
- `apps/dashboard/src/App.jsx`에서 `store-001` 샘플 화면을 확인하고 작업을 시작한다.
- React와 Node는 따로 설치하지 않고 Docker 컨테이너를 사용한다.

## Git 작업

브랜치 용도:

- `main`: 발표 가능한 상태만 유지
- `develop`: 팀원 작업을 합치는 통합 브랜치
- `feature/작업이름`: 개인 작업 브랜치

1. `develop`에서 자신의 작업 브랜치를 만든다.
2. 자신의 담당 폴더만 수정한다.
3. 작업이 끝나면 `develop`을 대상으로 PR을 연다.
4. 담당 폴더 변경은 직접 확인한 뒤 병합해도 된다.
5. 공통 API, Docker, JSON 형식은 팀에 알리고 확인받는다.
6. 개인 작업을 `main`에 바로 병합하지 않는다.

PR 본문에는 저장소의 간단한 확인 양식이 자동으로 나타난다. 승인 인원은 강제하지 않으며 `main`은 통합 확인이 끝났을 때만 갱신한다.

예시:

```bash
git switch develop
git pull
git switch -c feature/dashboard
```

## 문제가 생겼을 때

1. `docker compose ps`로 컨테이너 상태를 확인한다.
2. `docker compose logs api` 또는 `docker compose logs db`를 확인한다.
3. `/health`가 응답하는지 확인한다.
4. API 규격 변경이 필요하면 임의로 수정하지 않고 팀에 기록한다.
5. Docker 문제가 바로 해결되지 않으면 오류를 기록하고 샘플 JSON으로 담당 기능 개발을 계속한다.
6. 샘플 JSON으로 확인한 기능은 Docker가 정상화된 뒤 API 연결을 다시 확인해야 완료로 본다.
