# CAFE 데이터셋 적합성 검토 (비전)

목적: 카페노아 영상에서 유리·원거리·가림으로 사람이 누락되는 구간을 개선하기 위해,
CAFE 데이터셋이 YOLO 파인튜닝에 쓸 수 있는 사람 라벨을 제공하는지 확인한다.
본 이슈는 **적합성 판단까지**만 다루며 전체 학습은 하지 않는다. 수치는 로컬 실측.

> 검토 결과: 원거리·유리 미탐지 개선 용도로는 부적합하나(4절), 프로젝트를 **근접 실내
> 다매장**으로 재정의하는 데는 적합하여 **CAFE로 전환하여 진행**하기로 한다(7절).
> 실제 변환·학습은 다음 이슈로 분리한다.

| 항목 | 내용 |

## 2. 라벨 구조 (실측 샘플)

- 세그먼트별 `ann.json`(Supervisely 형식) + 전역 `evaluation/gt_tracks.txt`(MOT 형식) 병행.
- `ann.json`: figure(track)마다 keyframe box + 활동 라벨. 좌표 `[[x1,y1],[x2,y2]]` 픽셀.
- `gt_tracks.txt`: `프레임 ? ? x1 y1 x2 y2 그룹ID 활동` (약 360만 줄).
- **추적 ID 제공** → ByteTrack 정량 평가에도 활용 가능.
- 각 세그먼트 = 30프레임(6프레임 간격), 카페당 수백 세그먼트(카페당 약 14,000장).
- 인접 세그먼트는 시간 연속(픽셀차 5 이하) → 순서 배열 시 연속 재생 가능.

## 3. 바운딩박스 기준: 전신 vs 보이는 신체 (실측)

- bbox 가로세로비 h/w **평균 1.9**(전신 2~3 범위). 머리박스(≈1.0)가 아님.
- 즉 **전신(full-body) 기준** → 발 위치 기반 구역·좌석 판정과 호환.
- (참고: 카페노아 AI Hub 라벨은 머리박스 h/w≈1.0이라 발 위치 산출 불가였음. CAFE는 이 문제 없음.)

## 4. 카페노아 유사 장면(유리·원거리·가림) 존재 여부 — 핵심

| 카페노아 미탐지 원인 | CAFE에 유사 장면 있나 |
|---|---|
| **원거리(작은 사람)** | ❌ 없음. bbox 높이 중앙 292px, **80px 미만 0.0%** (전부 근접) |
| **유리 너머(반사·왜곡)** | ❌ 없음. 카메라가 매장 내부에서 직접 촬영(유리 격벽 없음) |
| **가림/밀집** | 🟡 일부. 테이블 착석·중첩으로 중간 수준 가림 존재(~11명/프레임) |

**결론적 관찰: CAFE는 전부 "근접 실내" 장면이라, 카페노아가 실제로 놓치는
원거리·유리 장면을 담고 있지 않다.** 가림만 일부 유사하다.

## 5. YOLO 라벨 변환 가능 여부 (실측)

- 변환 스크립트로 keyframe 박스를 YOLO txt(정규화 cx cy w h, class=person)로 변환 성공.
- 샘플 결과: 학습 9,587 / 검증 1,056 이미지, 박스 109,484개, `data.yaml` 생성.
- 라벨 시각화로 전신 박스 정확히 대응 확인.
- **변환 가능함이 확인됨.**

## 6. 참고: 예비 파인튜닝 관찰 (본 이슈 범위 밖, 근거용)

소규모 파인튜닝(9.5k장, 25epoch) 후 카페노아 비교 시:
- 067(근접 실내) +2.7%, 그러나 066(원거리 외부) 84%→2%, 071·068 하락.
- 원인: CAFE에 원거리·유리 장면이 없어, 그쪽 탐지 능력이 오히려 손상(도메인 편중).
- 이는 4절 결론(유사 장면 없음)과 일치한다.

## 7. 결론: CAFE 데이터셋으로 전환하여 진행

프로젝트 방향을 **"프랜차이즈 본점의 다매장 실내 혼잡도 관리"**로 재정의함에 따라,
비전 데이터셋을 카페노아에서 **CAFE로 전환하여 진행한다.**

### 7.1 전환 배경
- 기존 목적(카페노아의 유리·원거리 미탐지 개선)은 그에 맞는 원거리·유리 데이터가 필요하며,
  CAFE로는 해결되지 않는다(4절). 이 방향은 별도 데이터 확보 과제로 분리한다.
- 대신 서비스 컨셉을 **여러 매장의 실내 혼잡도를 본점에서 관리**하는 형태로 잡으면,
  근접 실내·다매장이 핵심이 되고 원거리·유리 문제 자체가 적용 대상에서 빠진다.

### 7.2 전환 근거 (CAFE 우위)
| 요구 | 카페노아 | CAFE |
|---|---|---|
| 다매장(프랜차이즈) | 1개 매장뿐 | **서로 다른 6개 카페** |
| 근접 실내 탐지 | 85~88% | **97% mAP**(자기 도메인 검증) |
| 라벨 형식 | 머리박스(발 위치 불가) | **전신박스(구역·좌석 판정 가능)** |
| 추적(ByteTrack) 검증 | 프레임 간격 커 불가 | **연속+추적ID 제공** |
| 시간대별 혼잡 데모 | 662장 연속 | 세그먼트 순서 배열 시 연속 |
| 대기시간(ETA) | 실외 줄 | **카운터 대기(Queueing/Ordering)** ROI로 산정 |

### 7.3 전환 시 대상에서 빠지는 것 (감수)
- **실외 대기줄·유입**(카페노아 066): CAFE에 없음 → 대기시간은 "카운터 대기"로 재정의.
- **원거리·유리 미탐지 개선**: 이번 방향의 대상이 아님(근접 실내라 해당 없음).

### 7.4 진행 계획 (다음 이슈로 분리)
1. CAFE 6개 중 데모용 매장 2~3개 선정(뷰·혼잡도 다양성).
2. 매장별 ROI(대기·직원) 지정 → `roi_zone_counter` 로직 재사용(다매장 집계는 `cafe_stores.py`).
3. 소규모 변환·학습으로 CAFE 매장 정확도 확인(전체 학습은 이후).
4. 카운터 구역 기반 대기시간 로직, 매장별 store_id 전송 구조 정리.

### 7.5 팀 확인 사항 (선행)
- 대기시간을 "실외 줄 → 카운터 대기"로 재정의: AICC(C)·백엔드(A) 합의.

**요약: CAFE는 카페노아의 원거리·유리 미탐지를 고치는 용도로는 부적합하나,
프로젝트를 근접 실내 다매장으로 전환하는 데는 적합하다. 이에 CAFE로 전환하여 진행하며,
실제 변환·학습은 다음 이슈에서 다룬다.**
