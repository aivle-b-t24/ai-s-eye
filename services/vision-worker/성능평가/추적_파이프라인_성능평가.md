## 1. 세그먼트 연속성 정정

CAFE의 숫자 세그먼트는 각각 다른 장면이 아니라 대부분 이어지는 영상이다.

- 카메라 5 일반 경계 531개의 160×90 grayscale MAD 중앙값은 `4.34`, 검수된 큰 장면
  전환 10개의 중앙값은 `27.42`였다.
- 카메라 21 일반 경계 392개의 중앙값은 `2.99`, 큰 장면 전환 5개의 중앙값은 `48.00`이었다.
- 일반 경계에서는 ByteTrack과 공개 ID를 유지하고, manifest로 확인한 장면 전환이나
  세그먼트 누락에서만 tracking epoch를 변경한다.

`gt_tracks.pkl`의 ID는 세그먼트 로컬 값이므로 16개 고정 검증 구간 안의 일반 경계
32개를 마지막/첫 프레임 위치로 연결했다. 344명을 연결했고 1명은 새 등장으로 판정했다.
같은 전역 ID는 같은 색으로 표시한 contact sheet를 사람이 대조했으며 잘못 이어진 경계는
발견되지 않았다. 좌표가 모두 같은 placeholder 정답 행은 평가에서 제외했다.

## 2. 고정 평가 조건

- 모델과 입력 영상은 모든 설정에서 동일하다.
- 카메라별 15초 구간 8개(일반 3, 혼잡·가림 3, 장면 전환 2), 총 1,200프레임을
  튜닝 600프레임과 held-out test 600프레임으로 고정했다.
- 튜닝에서만 8개 조합을 비교하고 test는 최종 1회 비교에 사용했다.
- 선택 규칙은 IDF1, 동률이면 HOTA, 다시 동률이면 FP 순이다.
- 처리속도는 LIVE worker가 함께 동작한 상태의 실측값이다.

## 3. held-out test 결과

| 설정 | IDF1 | HOTA | ID Switch | Precision | Recall | 인원 MAE | 속도 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 기존: 장면 전환 초기화 없음 | 92.524 | 82.312 | 12 | 99.106% | 92.659% | 0.723 | 37.49fps |
| **현재 기본: 실제 전환만 초기화** | **94.248** | **83.651** | **12** | **99.107%** | **92.768%** | **0.712** | **39.45fps** |
| 저신뢰 후보 `h25-b10-m75` | 93.702 | 83.362 | 18 | 98.913% | 92.984% | 0.685 | 39.19fps |

현재 기본 설정은 기존보다 IDF1이 `1.724%p` 높고, 실제 장면 전환 뒤 이전 공개 ID를
재사용한 사례는 0건이다. 반면 저신뢰 후보는 기존 대비 IDF1이 `1.178%p` 오르는 데
그쳤고 ID Switch가 `12→18`로 50% 증가했다.

따라서 사전 합격 기준인 IDF1 `+3%p`, ID Switch `30% 이상 감소`를 충족하지 못해
저신뢰 후보를 기본값으로 승격하지 않는다. 운영 프로필은 `conf=0.30`과 Ultralytics
기본 ByteTrack을 유지하고, 검증된 장면 전환·누락에서만 트래커를 초기화한다.

## 4. 카메라별 결과

| 카메라 | IDF1 | HOTA | ID Switch | Recall | 인원 MAE |
|---|---:|---:|---:|---:|---:|
| 5 | 95.920 | 85.697 | 3 | 95.006% | 0.540 |
| 21 | 92.511 | 81.526 | 9 | 90.479% | 0.883 |

카메라 21이 카메라 5보다 Recall이 `4.527%p` 낮아, 남은 개선 대상은 트래커 설정보다
카메라 21의 탐지 미스다.

## 5. 미탐지 원인과 파인튜닝 판단

held-out 6,457개 GT를 IoU 0.5 기준으로 다시 매칭했다.

| 구분 | Recall | 미탐지/GT |
|---|---:|---:|
| 전체 | 92.768% | 467 / 6,457 |
| 착석 활동 | 91.301% | 119 / 1,368 |
| 비착석 활동 | 93.162% | 348 / 5,089 |
| 다른 사람 bbox가 15% 이상 겹침 | 90.612% | 466 / 4,964 |
| 겹침 없음 | 99.933% | 1 / 1,493 |
| Eating/Drinking | 85.071% | 63 / 422 |
| Ordering | 82.879% | 44 / 257 |

미탐지 bbox 높이 중앙값은 `290px`, 탐지 성공은 `332px`였다. contact sheet 검수에서도
작은 사람 자체보다 카운터·테이블 주변에서 사람끼리 크게 겹치는 경우가 대부분이었다.

결론은 **선택적 파인튜닝을 다음 단계로 진행할 근거가 있다**이다. 단, 현 모델을 즉시
교체하지는 않는다. 카메라 21, Ordering, Eating/Drinking, 심한 중첩 사례를 우선으로
연속 영상 단위 train/validation/test를 분리한 3만~5만 장을 구성하고, 현재 held-out에서
Recall·인원 MAE와 추적 IDF1이 함께 좋아질 때만 새 모델을 채택한다. RIFE 보간이나
150GB 전체 무작정 학습은 하지 않는다.

## 6. 운영 확인

- 조건: baseline, 카메라 5·21 각 앞 5개 세그먼트, 총 332프레임
- 범위: YOLO 사람 탐지 + Pose + ByteTrack + 분석/원본 JPEG 생성·업로드 + StoreState·
  Occupancy API 전송까지 포함
- 콜드 스타트 포함 332프레임을 23.72초에 처리해 합산 `14.0fps`를 기록했다.
- 워밍업 후 두 매장 상태 한 쌍의 API 도착 간격 중앙값은 `0.538초`로, 영상 입력 환산
  약 `18.6fps`다. 실시간 1배속에 필요한 합산 10fps는 통과하지만 2배속 목표 20fps에는
  약 7% 부족하므로 장시간 2배속에서는 조금씩 지연될 수 있다.
- 프로세스 CPU는 단일 코어 기준 94%, 최대 RSS는 약 1.56GiB였다.
- GPU는 다른 데스크톱 부하가 있는 상태에서 연산 사용률 최고 49%, 전체 사용 VRAM 최고
  3,639/8,192MiB, 전력 최고 104W, 온도 최고 65°C였다.
- Occupancy GET 응답은 중앙값 `3.35ms`, p95 `4.98ms`였고, publish 후 100ms 간격
  폴러가 새 프레임을 확인한 시간은 중앙값 `68.9ms`, p95 `116.4ms`였다.
- Dashboard는 0.5초마다 확인하고 위치를 0.9초 동안 이동시키므로 API 게시 후 화면 이동
  시작은 최악 약 0.5초, 이동 완료는 약 1.4초 이내가 목표다.
- 실제 POST 뒤 두 매장 모두 직원 1명, 모든 agent의 bbox 포함, 원본·분석 이미지 HTTP
  200을 확인했다.

## 7. 디지털 트윈 2.5D 보정

- 화면 위치는 YOLO bbox 하단 중앙인 발 좌표를 그대로 사용한다.
- 사람 크기는 발 위치 원근 곡선과 정규화 bbox 높이를 결합한다. 카메라별 bbox 높이
  기준은 카메라 5 `0.32`, 카메라 21 `0.27`이고 시뮬레이션 고객처럼 bbox가 없으면
  기존 원근 곡선만 사용한다.
- 15px 이내 좌표 변화는 정지 흔들림으로 무시하고, 그보다 큰 이동이 두 번 연속
  관측됐을 때 0.55 비율로 보간한다.
- 착석 고객은 150px 이내 좌석 앵커에 붙고, 220px를 벗어나기 전까지 같은 좌석을
  유지한다.
- 사람과 테이블의 z-index는 발 위치와 테이블 앞쪽 모서리로 계산해, 테이블 뒤 사람은
  가리고 테이블 앞 사람은 앞으로 보이게 한다.
- 직원이 잠시 가려지면 StoreState 직원 수와 같은 ID의 마지막 아이콘을 함께 유지하고,
  아이콘을 반투명한 `일시 가림` 상태로 표시한다.

원근 단조 증가, bbox 크기 반영, bbox 없는 시뮬레이션 호환, 테이블 앞뒤 가림, 좌석
배정·유지, 정지 흔들림 억제는 Dashboard 단위 테스트로 고정했다.

원본 영상·가중치와 생성된 대용량 평가 산출물은 GitHub에 올리지 않는다. 재현 코드는
저장소에 포함하고 결과 수치와 검수 방법은 이 문서에 남긴다.
